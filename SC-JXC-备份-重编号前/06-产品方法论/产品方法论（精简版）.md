# 产品方法论（精简版）

> 本项目怎么做事。AI 和人都按这一页执行。

## 一、人在回路

- 人做判断：给输入、定范围、定优先级、做验收
- AI 做执行：读资料、整理、生成、修改、自查
- 发现 AI 方向跑偏，立刻喊"停"，在判断层纠正，不让它在错误方向上反复改

## 二、文档三层分离（每类信息只有一个家）

| 信息 | 放在哪 | 例子（以"采购数量"为例） |
| --- | --- | --- |
| 字段事实 | 字段清单 TSV | 整数，大于 0，用户填写 |
| 业务规则 | 业务主PRD | 提交审核时每行都必须填写；审核后不可改；入库数量累计不能超过它 |
| 页面交互 | Demo PRD | 数字输入框，离开时校验，错误显示在本行下方 |

三段话不是重复，是在回答三个不同的问题：字段是什么、业务怎么限制、页面怎么让人完成操作。字段只在 TSV 里写一次，不在 md 里留副本。

## 三、PRD 套件与评审PRD

- **PRD 套件（开发依据）**：字段清单 TSV + 主PRD + Demo PRD + 原型标注
- **评审PRD（拍板依据）**：把套件浓缩成一份，给业务负责人看，全中文、大白话
- 权威排序：字段清单 TSV > 主PRD > Demo PRD > 原型标注。评审PRD 只转译，不造数据
- `08-相关资料`（竞品调研、接手项目的旧资料）只作参考，不进权威排序；引用注明出处，冲突标【待确认】
- 评审后有改动，要回写到对应的权威来源，保证套件和评审PRD 一致

### 产出顺序

1. 盘点：上游资料齐不齐，缺了先补
2. 字段清单 TSV
3. 主PRD（状态、动作、规则）
4. Demo PRD（列表页、新增编辑页、详情页）
5. 前端原型（照着文档画，不自己加东西）
6. 原型标注
7. 评审PRD → 评审 → 改动回写权威来源

不过关不往下走。上一步有问题，先回上一步改。

## 四、改动入口表（需求变了先改哪）

| 变化类型 | 先改哪里 | 再检查哪里 |
| --- | --- | --- |
| 字段名称、类型、必填、来源、取值变了 | 字段清单 TSV | 主PRD、Demo PRD、原型 |
| 状态、动作、业务规则变了 | 主PRD | Demo PRD、原型、标注 |
| 页面布局、控件、提示文案变了 | Demo PRD | 原型、标注 |
| 已拍板的结论变了（如评审会上改了审核金额线） | 拍板记录（末尾追加一条新结论，不改原文） | 字段清单、主PRD、Demo PRD、原型 |
| 跨模块流程变了 | 01-全局背景信息 | 相关模块全部文件 |

只在聊天里纠正、只改原型不改文档，都等于没改。

## 五、版本迭代

- 第一版做完后保留不动，作为对照基线
- 新需求在 `03-产品设计` 下新建版本文件夹（如 `20261020-第二版迭代/`），只放本轮相关内容
- AI 默认读当前版本目录，需要对比时才读旧版本

## 六、和 AI 协作的规矩

1. **五段式提示词**：Context（背景）/ Request（要做什么）/ Output format（交成什么样）/ 红线禁止（不许做什么）/ Checkpoint（什么时候汇报）
2. **谋定而后动**：先盘点依赖和现状，缺地基先汇报，不硬做
3. **事实要查证**：不确定的标【待确认】，不靠猜
4. **独立核验**：AI 说"完成了"不算数，人或另一个 AI 对照权威来源检查才算数

## 七、背景：产品迭代的飞轮（不作为执行规则）

先跑通最小闭环（一期：订单、出入库、库存），再积累真实数据（二期：报表、批次），数据够了再长出智能（三期：补货建议）。不求一步到位。
